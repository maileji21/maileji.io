# 小红书数据采集与入库管道

基于 DrissionPage 监听小红书搜索接口，把关键词搜索结果结构化采集下来，落库 SQLite，支持增量去重与采集质量统计。

采集字段：标题、作者、作者 ID、点赞、收藏、评论、分享、笔记链接、首次采集时间、最近采集时间、被采集次数。

## 核心指标

| 指标 | 数值 | 说明 |
|---|---|---|
| 单关键词采集 | 30 页 / 600 条 | 平均 19s 每页（含滚动触发懒加载的等待） |
| 累计入库 | 950 条唯一（1200 条次） | 多关键词、多轮次采集累计 |
| 互动字段缺失率 | 0% | 清洗后统计，无法解析的脏值置 NULL 而非 0 |
| 同词跨天重跑重复率 | 41.7% | UPSERT 幂等合并，库里没有重复行 |
| 非笔记条目跳过率 | 2% | 热搜位、推荐位自动过滤 |

## 设计要点

- **监听接口而不是解析 DOM**：接口返回本身就是结构化 JSON，比用 XPath 抓渲染后的页面稳定得多，也不会因为改版换 class 就崩。代价是请求带 x-s / x-t 签名，必须跑在真实浏览器里，不能换成 requests 直接请求。
- **幂等入库**：以 `(platform, note_id)` 为复合主键，配合 `ON CONFLICT DO UPDATE`。同一条笔记被再次采到时，只更新互动数并把 `seen_count + 1`，不产生重复行——重复率可以直接从数据里算出来（`1 - COUNT(*) / SUM(seen_count)`），不需要额外写去重脚本。
- **脏字段清洗**：`1.2万` / `10万+` / `3,456` / `赞` 这类值统一换算成整数，解析不了置 NULL 而不是 0。这一步是为了不把"缺失"污染成"零互动"，否则平均值和排序全是错的。
- **采集质量落表**：每页的结果都写进 `crawl_log`（原始条数、新增、重复、跳过、耗时），跑完能直接看出哪一页异常，而不是只看到一个总数。
- **提前终止**：连续 2 页没有新增就判定该关键词已采完，避免在无效翻页上浪费时间。

## 文件结构

```
collect.py             采集主程序：监听接口、翻页、解析、落库
storage.py             清洗 parse_count / UPSERT save_notes / 统计 stats
init_db.py             建表：notes（笔记）+ crawl_log（采集日志）
小红书笔记数据.csv       一次真实采集的导出数据，950 条，可直接看字段与质量
```

## 怎么跑

```bash
pip install drissionpage

python init_db.py    # 建表，生成 xhs.db
python collect.py    # 要采的关键词在 collect.py 底部的列表里改
```

首次运行会打开 Chrome，需要手动扫码登录小红书，登录态保存在 `./browser_data/`，之后复用。数据库 `xhs.db` 是运行时生成的，不在仓库里。

## 已知限制

- 接口请求带 x-s / x-t 签名，只能靠真实浏览器发请求，做不了纯 requests 的高并发方案，这是这套方案最大的吞吐瓶颈。
- 翻页依赖页面懒加载触发，滚动节奏太快会拿不到响应，单页约 19s，速度上不去。
- 小红书有风控，需要控制频率。我的做法是词与词之间停 8 秒，每天只跑少量关键词。
- 数据仅用于个人学习研究，不做二次分发。
